# 开发实施规范

## 目标

按照项目实际约定和最小可交付单元逐个形成纵向闭环。每完成一个真实环节，更新需求文件中对应单元的进度表。

## 阶段接口

- **输入**：由 `lohaaa-plan` 产出的需求文件，至少包含范围、方案、模块归属、最小可交付单元和完成标准。
- **缺失处理**：范围或关键方案不明确时回到 `lohaaa-plan`，不得在编码阶段自行扩大或猜测需求。
- **输出**：实现完成且经过实际运行验证的单元；单元进度进入“待验收”。
- **下一技能**：`lohaaa-check`。若用户已授权完整交付，完成一个单元后直接进入单元验收，不在阶段边界停止。
- **状态更新**：进入本技能时将需求文件的当前阶段设为“开发实施”、状态设为“进行中”；实现进度仍只写在当前功能单元下面。

## 一、规范优先级

发生冲突时依次判断：

1. 正确性、安全性和明确需求约束
2. 当前语言、框架和运行版本的官方规范
3. 项目已有且仍然有效的强制约定
4. Clean Code 原则
5. 成熟社区和团队约定
6. 个人偏好

官方实践必须匹配项目实际版本。项目惯例只是风格差异时保持一致；涉及官方废弃、安全或正确性风险时，修改本需求涉及的必要范围，不借机全项目重构。

## 二、编码与设计原则

- 名称使用业务语言并准确表达职责。
- 模块高内聚，公开接口最小且稳定。
- 控制流清楚，避免深层嵌套和隐藏副作用。
- 错误必须正确处理，禁止静默吞掉。
- 数据所有权、状态转换和事务边界清楚。
- 优先简单直接的实现，不为假设中的未来添加扩展层。
- 抽象建立在稳定且真实的共同点上，不因两处表面相似立即抽取。
- 不为缩短函数制造无意义的一行包装。
- 不把所有实现都包装成接口或设计模式。
- 在性能敏感路径避免不必要的分配、复制、查询和重复计算。
- 修改公开接口前必须定位并迁移所有调用方；不保留无要求的旧别名或兼容层。

编码前确认：

```text
语言及版本：
框架及版本：
官方推荐和废弃方式：
项目格式化和静态检查工具：
项目命名、错误、日志和模块模式：
当前单元涉及的公开接口及调用方：
```

## 三、逐单元实施

每次只推进一个最小可交付单元：

```text
选择单元
→ 明确行为和验收场景
→ 设计实体与规则
→ 定义 API 或调用契约
→ 实现逻辑
→ 实现前端或客户端
→ 实际运行验证
→ 更新进度为待验收
```

不得先铺开整个需求的所有实体、API 或页面，再集中联调。

### 行为定义

编码前写清：

```text
使用者或调用方：
前置条件：
触发操作：
输入：
系统行为：
成功结果：
失败结果：
权限限制：
边界情况：
```

这些内容必须与需求文件中的完成标准一致。

## 四、实体与数据设计

从业务规则而非表单字段或数据库表开始：

- 实体身份和核心属性
- 属性约束和业务不变量
- 状态及合法状态转换
- 创建、修改和删除规则
- 实体关系和生命周期

根据复杂度区分：

| 模型 | 职责 |
|---|---|
| 领域实体 | 表达业务规则和状态 |
| 持久化模型 | 适配数据库存储 |
| 请求模型 | 表达调用方允许提供的数据 |
| 响应模型 | 表达调用方需要的数据 |
| 前端视图模型 | 表达页面展示和交互状态 |

简单项目可以复用结构，但不得因此暴露数据库内部字段、敏感数据或服务端专属状态。

## 五、API 契约

API 根据使用场景设计，不按数据表机械生成增删改查。明确：

```text
用途和调用方：
操作名称、路径和方法：
认证与权限：
请求参数：
成功响应：
业务错误和状态码：
幂等性：
分页、排序或筛选：
并发和事务行为：
版本兼容：
```

规则：

- 输入只包含调用者允许控制的数据。
- 输出只返回调用者需要且有权看到的数据。
- 认证和授权分开处理。
- 写操作根据风险处理重复请求和并发冲突。
- 不返回内部异常、堆栈、令牌或敏感数据。
- 前后端并行时先固定最小契约，再分别实施。

## 六、后端业务逻辑

推荐依赖方向：

```text
接口或传输层
→ 应用流程
→ 业务规则
→ 基础设施实现
```

一个 API 单元应完成：

1. 输入格式和业务约束校验。
2. 身份和权限验证。
3. 加载所需状态。
4. 执行业务规则。
5. 在正确事务边界内保存数据。
6. 调用必要外部能力并处理失败。
7. 返回稳定结果和业务错误。
8. 记录必要但不敏感的日志或指标。

接口入口不得堆积业务逻辑；外部服务失败后不得留下无法解释的半完成状态。

## 七、页面级功能

页面实现不能只覆盖理想路径。根据需求处理：

- 初始、加载和正常数据状态
- 空状态
- 输入错误和服务端业务错误
- 网络或系统错误
- 无权限状态
- 提交中和重复操作
- 成功反馈及成功后的状态同步
- 键盘操作、焦点和必要可访问性
- 目标屏幕尺寸、长文本和真实数据

客户端校验改善体验，但不能代替服务端校验和权限检查。页面不得直接依赖数据库模型或内部错误格式。

## 八、API 客户端

一个客户端单元应完成：

1. 确认上游官方契约和版本。
2. 定义请求、响应和公开调用接口。
3. 实现认证、序列化和资源释放。
4. 设置合理超时。
5. 只按上游语义和幂等条件实施重试。
6. 将上游错误映射为稳定、可理解的错误。
7. 避免在日志中输出令牌和敏感内容。
8. 通过真实或受控协议环境验证调用。

只生成类型或只包装 HTTP 请求不算完成。

## 九、实施中的进度更新

进入环节时标记为“进行中”；完成并得到可核查结果后标记为“已完成”。缺少外部条件时标记“阻塞”并写明解除条件。所有实现环节完成后，将单元整体推进到“待验收”。

进度结果应写事实，例如：

```text
已完成：取消订单接口返回最新订单状态，状态冲突使用 409。
阻塞：测试环境缺少支付平台回调地址，需要生产运维配置。
```

不得写内部推理、讨论流水或主观百分比。

## 阶段完成标准

- 当前单元的实体、契约、逻辑和交付表面已经形成完整闭环。
- 所有调用方同步迁移，旧路径和无用代码已经清理。
- 正常、失败、权限和关键边界已实际运行验证。
- 没有占位、假数据、空操作或未连接入口。
- 需求文件进度与实际状态一致，单元进入待验收。

## 下一阶段

当前单元实现完成并实际运行验证后，使用 `lohaaa-check` 执行单元验收和质量检查。验收未通过时回到本技能修复同一单元，再重新验收。
