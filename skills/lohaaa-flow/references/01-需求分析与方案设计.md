# 需求分析与方案设计

## 目标

在编码前确定实际问题、可接受范围、最佳可行方案、最小可交付单元以及项目和模块边界。产出一份可持续更新的需求文件。

## 一、用通俗语言理解需求

先回答：

```text
谁遇到了什么问题？
希望最终得到什么结果？
怎样才算完成？
哪些内容明确不在本次范围？
```

将答案写入需求文件。表达必须让不熟悉技术实现的人也能理解，不得直接以框架、数据库或组件名称代替业务目标。

同时明确：

- 目标用户或调用方
- 前置条件
- 正常结果
- 失败和边界结果
- 性能、安全、兼容性等实际约束
- 非目标
- 验收标准

## 二、选择调研方式

### 已处理过的内容

1. 回顾现有实现和已知方案。
2. 检查当前官方推荐、维护状态和废弃说明。
3. 搜索是否有更成熟或更现代的方案。
4. 比较新方案是否真正降低当前项目的总成本。

### 没接触过的内容

1. 优先阅读当前版本的官方文档、规范和安全指南。
2. 补充权威实现、维护者说明和成熟生产案例。
3. 识别常见错误、边界和失败模式。
4. 用通俗语言重新解释需求和推荐方案，确认已经理解而非只复制术语。

### 调研规则

- 官方和一手资料优先。
- 检查资料是否适用于项目实际版本。
- 不以“更新”或“功能更多”直接判定更好。
- 不为搜索而搜索；已有证据足以决策时停止扩展范围。
- 高不确定性问题用最小实验验证关键假设，不提前实现完整方案。

## 三、比较并选择方案

至少比较项目常用方案与现代化候选方案。根据场景调整权重：

| 维度 | 需要回答的问题 |
|---|---|
| 需求匹配 | 是否完整解决当前问题？ |
| 兼容性 | 是否适配现有架构、版本和部署环境？ |
| 稳定性 | 是否经过生产验证并持续维护？ |
| 复杂度 | 引入多少代码、配置、依赖和间接层？ |
| 迁移成本 | 需要修改多少现有数据和调用方？ |
| 维护成本 | 六个月后是否容易理解、排查和升级？ |
| 性能与资源 | 是否满足真实规模，是否有多余分配、复制或计算？ |
| 安全性 | 默认行为是否安全，是否存在已知风险？ |
| 生态 | 文档、工具链和集成是否成熟？ |
| 可逆性 | 失败后能否低成本回退或替换？ |

记录：

```text
候选方案：
关键差异：
需要验证的假设：
最终选择：
选择理由：
接受的代价：
未选择其他方案的原因：
重新评估条件：
```

最佳方案是当前约束下可靠解决问题且总成本合理的方案，不是技术最新的方案。

## 四、建立需求大纲

从最大需求集逐层拆分：

```text
需求总目标
└─ 业务能力或核心流程
   └─ 功能模块
      └─ 页面、用户流程或系统能力
         └─ 最小可交付单元
```

每拆一层检查：

- 子项合起来是否覆盖父项？
- 子项是否重复或职责交叉？
- 同一层的抽象粒度是否接近？
- 每项是否能追溯到业务目标？
- 依赖和待确认信息是否明确？
- 正常、空、失败、权限和中断路径是否遗漏？

## 五、确定最小可交付单元

### 页面级功能单元

一个页面中可独立使用、运行和验收的用户功能。复杂页面必须继续拆分。例如“订单详情页”可拆为查看信息、取消订单、支付订单和申请售后。

### API 客户端单元

一个完整的上游 API 能力，包括请求和响应类型、认证、序列化、超时、上游规定的重试、错误映射和调用验证。

### 后端 API 单元

一个对外暴露的 API 行为，包括契约、身份和权限、输入校验、业务规则、数据处理、错误响应和实际请求验证。

最小单元必须：

- 目标单一且对用户或调用方有价值。
- 输入、输出、依赖和边界明确。
- 可以独立实现和验证。
- 有清楚的完成标准。
- 不依赖占位或未实现步骤才能演示。

## 六、确定项目与模块边界

### 新项目

根据已知职责、运行方式、数据所有权和真实变化方向设计最简单的可演进结构。不得为想象中的未来需求预建架构。

### 已有项目

先调查：

- 项目入口、构建和依赖配置
- 现有模块和类似实现
- 命名、目录、错误处理和测试约定
- 模块引用和公开接口
- 数据访问、部署和运行方式

优先沿用现有模式，禁止引入第二套目录、分层或抽象方式。

### 边界决策

```text
现有模块能自然承载 → 放入现有模块
职责独立但仍属于同一系统 → 建立项目内模块
具备清晰业务、数据、部署或生命周期边界 → 考虑独立项目
```

代码量大或业务重要本身不足以成为独立项目。独立后仍需频繁访问主项目内部状态、同步发布或跨边界修改时，应优先保留为项目内模块。

每个模块记录：

```text
职责：
对外接口：
拥有的数据：
依赖的模块：
被哪些模块调用：
允许的依赖方向：
禁止直接访问的内部内容：
对应需求单元：
```

## 七、建立需求文件并内嵌进度

优先复用项目已有需求文档位置；无约定时使用 `assets/需求文件模板.md`。

每个最小可交付单元必须包含：

- 需求说明和单元类型
- 前置条件和业务规则
- 实现范围和完成标准
- 进度表
- 验收结果

进度表放在对应单元下面，禁止另建独立进度文件。只使用：待处理、进行中、阻塞、待验收、已完成、不适用。

需求文件不得包含内部思考过程、对话摘录、调试流水或无长期价值的解释。

## 阶段完成标准

- 需求本质、范围、非目标和验收标准明确。
- 调研来源和方案决策足以支撑实施。
- 最大需求集已经拆到可独立验收的单元。
- 每个单元归属明确并带进度表。
- 项目、模块、数据和依赖边界已经确定。
- 没有未解决且会改变整体方案的关键问题。
