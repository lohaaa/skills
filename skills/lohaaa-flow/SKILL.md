# 软件需求交付工作流

用一套可追踪的闭环流程交付软件需求。需求文件既记录范围和验收标准，也在每个最小可交付单元下记录实时进度；不得另建重复的进度表。

## 核心流程

```text
理解需求
→ 调研并比较方案
→ 拆分最小可交付单元
→ 确定项目与模块边界
→ 逐单元设计、实现和验证
→ 单元验收
→ 模块统一验收
→ 代码与页面质量检查
→ 发布准备、上线和生产验证
```

## 何时使用

以下任务应使用本技能：

- 从需求分析开始实现一个软件功能。
- 设计并交付较完整的模块。
- 实现页面级功能、API 客户端或后端 API。
- 需要比较常用方案和现代化方案。
- 需要建立带内嵌进度的需求文件。
- 需要进行单元验收、模块验收或发布准备。

纯知识问答、只解释现有代码且不产生交付物时，不必建立完整需求文件。

## 开始工作

1. 读取项目的现有结构、配置、约定和相似实现，禁止直接套用新的目录或架构。
2. 查找项目已有的需求文档位置和格式；存在约定时必须复用。
3. 没有既有约定时，使用 [需求文件模板](assets/需求文件模板.md) 建立需求文件。默认位置为 `docs/requirements/<需求名称>.md`；若项目不将工作文档纳入仓库，则在用户指定或当前工作载体中维护同等结构。
4. 每个最小可交付单元下必须包含自己的进度表。进度只在该处维护一次。
5. 按阶段读取对应参考文件，不要一次加载所有细节：
   - 分析、调研、拆分和架构边界：[需求分析与方案设计](references/01-需求分析与方案设计.md)
   - 编码规范和逐单元实现：[开发实施规范](references/02-开发实施规范.md)
   - 单元、模块和内容质量验收：[验收与质量检查](references/03-验收与质量检查.md)
   - 数据迁移、部署和上线：[发布准备与上线](references/04-发布准备与上线.md)

## 不可违反的规则

- 先用通俗语言说明“谁遇到什么问题，希望得到什么结果”。
- “现代化”不等于“最佳”；方案必须结合兼容性、稳定性、维护成本和现有架构比较。
- 已有项目先遵循实际结构。只有出现清晰的业务、数据、部署或生命周期边界，才拆成独立项目。
- 规范优先级：正确性与安全性，其次是当前版本官方规范、项目有效约定、Clean Code，最后才是其他社区或个人偏好。
- 以最小可交付单元纵向实现，禁止先铺开整个需求的所有实体、所有 API 或所有页面后再集中联调。
- 页面单元、API 客户端单元和后端 API 单元都必须形成可运行、可调用、可验收的闭环。
- 完成一个单元后立即验收；所有单元完成后再做模块统一验收。
- 不得用占位文案、假数据、空操作、固定成功响应、未连接按钮或 `TODO` 掩盖未完成工作。
- 代码注释只解释长期有效的原因和约束，不得写入思考过程、对话记录、调试过程或修改历史。
- 发布前必须确认代码之外的前置条件、发布后操作、生产验证和回滚路径。
- 用户已授权实施时，不得只交付计划或分析；持续工作到当前范围形成完整交付。

## 最小可交付单元

根据交付表面选择粒度：

| 类型 | 单元定义 | 完整闭环 |
|---|---|---|
| 页面级功能 | 一个页面中可独立使用和验收的用户功能 | 实体与规则、API、后端、前端、实际页面验证 |
| API 客户端 | 一个上游 API 能力 | 契约、类型、认证、调用、错误处理、实际或受控调用验证 |
| 后端 API | 一个对外暴露的 API 行为 | 契约、权限、校验、业务逻辑、数据处理、错误、实际请求验证 |

一个复杂页面应继续拆分。没有页面的任务不得强行套用页面粒度。

## 进度规则

每个单元下使用以下状态：

| 状态 | 含义 |
|---|---|
| 待处理 | 尚未开始 |
| 进行中 | 当前正在执行 |
| 阻塞 | 缺少外部条件，暂时无法继续 |
| 待验收 | 实现完成，尚未通过验收 |
| 已完成 | 已实现、验收并完成质量检查 |
| 不适用 | 当前单元不涉及该环节 |

禁止使用主观完成百分比。每完成一个实际环节立即更新对应单元的进度表，并在“结果或阻塞原因”中写入简洁、可核查的结果。不得记录内部思考过程。

模块状态由其单元和模块验收得出，不再维护第二套详细进度：

```text
存在实施中的单元 → 进行中
存在无法推进的关键单元 → 阻塞
所有单元完成但模块未统一验收 → 待验收
所有单元完成且模块验收通过 → 已完成
```

## 完成门槛

### 单元完成

必须同时满足：

- 需求行为和边界已经实现。
- 实际运行路径验证成功。
- 单元验收通过。
- 代码规范、格式、注释和用户文案检查通过。
- 没有占位、假数据或临时实现。
- 需求文件中的单元进度和验收结果已经更新。

### 模块完成

必须同时满足：

- 所有下属单元完成。
- 完整业务流程和跨单元集成通过。
- 权限、数据一致性及必要回归检查通过。
- 模块统一验收结论已经记录。

### 需求发布

必须同时满足：

- 所有模块完成。
- 数据库、配置、基础设施和外部依赖等前置条件满足。
- 发布及发布后必做操作完成。
- 生产冒烟、日志指标和数据正确性验证通过。
- 需求文件记录最终发布结果。

## 按比例执行

小改动仍然保留一个最小可交付单元，但可以将确实不涉及的环节标记为“不适用”。不得为了形式制造空章节、无意义文档或无价值测试；也不得以任务较小为理由跳过实际运行验证和完成标准。
