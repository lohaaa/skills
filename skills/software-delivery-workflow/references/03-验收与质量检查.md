# 验收与质量检查

## 目标

用单元验收证明每个最小可交付单元独立正确，用模块验收证明单元组合后形成完整业务能力，并在最终交付前清除代码、注释和页面中的临时或无效内容。

## 一、两级验收

```text
单元实现完成
→ 单元验收
→ 修复并重新验收
→ 标记单元完成
→ 所有单元完成
→ 模块统一验收
→ 修复并重新验收
→ 标记模块完成
```

不得把单元内已知缺陷推迟到模块验收。

## 二、页面级功能单元验收

在实际页面中检查用户能否完成目标：

- 页面入口、数据加载和展示正确。
- 核心操作形成完整闭环。
- 前后端数据一致，刷新或重新进入后结果仍正确。
- 表单和输入校验正确。
- 加载、空数据、无权限、失败和成功状态完整。
- 重复点击、返回和中断不会产生错误状态。
- 错误反馈说明发生了什么以及用户可以做什么。
- 键盘、焦点、必要可访问性和目标屏幕尺寸可用。

不能只看代码或自动化测试，必须操作实际页面并观察结果。

## 三、后端 API 单元验收

通过实际请求验证：

- 正常请求和响应
- 非法输入和边界值
- 未认证与无权限
- 资源不存在和业务状态冲突
- 重复请求和幂等行为
- 并发修改和事务失败
- 数据持久化结果
- 状态码及错误结构
- 敏感信息保护
- 必要日志和可观测结果

验证的是调用方可观察行为，不是控制器、字段复制或模拟对象是否被调用。

## 四、API 客户端单元验收

检查：

- 路径、方法、参数和认证正确。
- 请求及响应序列化符合契约。
- 成功结果和错误映射正确。
- 超时、重试和资源释放符合上游规则。
- 日志不会泄露令牌或敏感数据。
- 调用方能通过公开接口完成目标。

优先使用真实测试环境；不可用时使用能验证协议边界的受控环境，并明确尚未覆盖的外部风险。

## 五、测试选择

测试是长期回归资产，不是完成证明的替代品：

- 业务规则和状态转换使用聚焦的单元测试。
- API 契约、权限、事务和数据边界使用集成测试。
- 跨页面或跨服务关键流程使用端到端验证。
- 简单且稳定的连接代码优先实际冒烟，不为“有测试”编写实现断言。
- 测试必须能够在合理缺陷出现时失败，禁止断言字段照抄、调用转发、源代码文字或“没有抛异常”。

永久测试完成后仍要运行实际功能。

## 六、单元完成门槛

单元只有同时满足以下条件才能标记“已完成”：

- 需求行为、失败和关键边界已实现。
- 实际功能运行验证通过。
- 需要保留的回归测试通过。
- 代码、注释和用户内容检查通过。
- 不存在占位或临时实现。
- 验收结果和证据已写回该单元。

## 七、模块统一验收

所有单元完成后检查：

### 需求覆盖

- 每个需求项都能追溯到完成的单元。
- 没有遗漏异常、权限或后台能力。
- 没有实现超出范围的功能。

### 完整业务流程

按照真实用户或调用方顺序执行创建、读取、修改、失败恢复和最终结果确认。重点检查跨页面、跨 API 和跨服务衔接。

### 集成与一致性

- 页面和 API 契约一致。
- 一个单元产生的数据能被后续单元正确使用。
- 状态修改能在其他入口正确反映。
- 权限、错误格式和术语在所有入口一致。
- 跨单元状态生命周期、并发和中断恢复正确。

### 回归

根据真实依赖检查现有功能、共享组件、公共 API、数据结构、权限系统和部署流程。不要机械扩大到无关范围。

## 八、代码规范和格式

使用项目已有工具执行格式化、静态分析、类型检查或编译。检查：

- 符合当前版本官方规范和项目约定。
- 命名准确，模块和函数职责清楚。
- 没有无效分支、未使用代码和重复业务规则。
- 没有无意义抽象、包装层和依赖。
- 错误没有被静默忽略。
- 没有调试输出、临时配置和开发开关。
- 修改范围只包含需求所需内容。

格式问题交给项目配置的格式化工具，禁止顺带格式化无关文件。

## 九、注释检查

保留解释长期有效原因和约束的注释，例如业务不变量、安全限制、兼容原因和第三方特殊行为。

删除：

- 思考过程和对话记录
- 开发步骤和调试流水
- 修改历史式说明
- 对明显代码的逐行复述
- 被注释掉的旧代码
- `TODO`、`FIXME`、`TBD` 或未兑现承诺

能通过准确命名和清晰结构表达时，不添加注释。

## 十、页面内容检查

在实际页面中确认：

- 用户第一眼能够理解标题、字段和操作。
- 文案使用用户熟悉的业务语言。
- 错误说明问题和可采取的下一步。
- 页面不暴露接口名、数据库字段、状态码或内部异常。
- 长文本、真实数据和目标屏幕尺寸布局正常。

删除：

- 面向开发者的说明和需求分析
- “功能开发中”“敬请期待”等占位文案
- Lorem ipsum、假用户名、假订单和示例统计
- 无实际作用的介绍性文字
- 未实现功能的按钮、菜单和链接
- 调试信息、堆栈和内部错误

加载、空数据、无权限和错误是产品真实状态，不是占位内容；必须根据用户任务给出准确说明。

## 十一、清理后的重新验证

任何清理都可能改变行为。完成格式、注释或文案调整后：

1. 重新运行受影响的静态检查、类型检查或编译。
2. 重新启动并操作受影响页面或 API。
3. 确认功能、布局和错误反馈仍然正确。
4. 更新需求文件中的验收结果。

## 模块完成标准

- 所有单元均为已完成。
- 完整业务流程和跨单元集成通过。
- 权限、数据一致性和必要回归通过。
- 代码、注释和页面内容符合要求。
- 清理后的实际功能重新验证通过。
- 模块验收结论已记录在需求文件中。
